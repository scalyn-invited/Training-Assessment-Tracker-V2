Nodes and ownership
  • Draft / autosave — Recoverable work (draft)
  • Submit attempt — Receipt + hashes (submit)
  • Queued grading — Quiz / AI draft (grade)
  • Validate grade — Evidence checks (validate)

  • Feedback — Appeal / human review (feedback)

  • Notify reviewer — Queued SMTP (notify)
Directed relationships
  1. draft → submit: Submit
  2. submit → grade: Queue after commit
  3. grade → validate: Provisional result
  4. validate → review: Save
  5. review → approve: Human decision
  6. approve → publish: Commit
  7. publish → feedback: Feedback
  8. review → regrade: Request changes
  9. regrade → grade: New grading attempt
  10. grade → failure: Provider / job failure
  11. failure → grade: Bounded retry
  12. review → notify: Queue mail
Immutable and fair
  • Resubmission creates a NEW submission; regrade creates a new grading attempt. Member appeal keeps original approval and uses another reviewer where possible.
  • No self approval. Concurrent review uses optimistic versions; overrides record reason. Only approved grades update official KPIs and normal API answers.
Failure and notifications
  • Invalid criterion, evidence or schema returns for correction/regrade; no zero score on technical failure. Provider outage leaves approved lessons and autosave usable.
  • SMTP failures do not lose submission or review queue: retry/dedup, bounce alert, recheck recipient access, record ambiguous acceptance; reminders and overdue escalation.
AI policy and cost
  • Two adapters + mock; per-task model/capability/privacy policies. Reserve cost before enqueue; reconcile tokens, rates and ambiguous timeout charges.
  • 90s provider / 120s job / 180s retry_after; three transient retries, capped concurrency and explicit allowlisted fallback. No model grants approval.
