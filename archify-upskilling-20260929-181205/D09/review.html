Nodes and ownership
  • Draft — Autosave (draft)
  • Submitted — Immutable receipt (submitted)
  • Queued — Durable job (queued)
  • Grading — Provisional only (grading)
  • Review pending — Coordinator gate (review-pending)
  • Approved — Immutable decision (approved)
  • Changes requested — New submission required (changes-requested)
  • Technical failure — Bounded retry (technical-failure)
  • Withdrawn — Before approval only (withdrawn)
Directed relationships
  1. draft → submitted: Submit
  2. submitted → queued: Commit + enqueue
  3. queued → grading: Claim job
  4. grading → review-pending: Validated result
  5. review-pending → approved: Human approval
  6. review-pending → changes-requested: More evidence
  7. grading → technical-failure: Job failure
  8. technical-failure → grading: Retry budget
  9. queued → withdrawn: Allowed withdrawal
Attempt identity
  • Resubmission starts a NEW draft/attempt linked to the old one; changes_requested never mutates an immutable submission.
  • Regrade from review_pending creates a new grading attempt on this submission, then returns to review_pending. Approved decisions can only be superseded with reason.
Review and appeal
  • Approve/override requires assigned alternate reviewer when self-enrolled; optimistic conflict prevents stale simultaneous decisions.
  • Appeal opens a separate review preserving the original approval. Approved and withdrawn are terminal for this decision; approved evidence drives KPIs.
Failure / withdrawal
  • Technical failure is not a zero score: preserve evidence and use bounded retry or human recovery. No submission data is lost when SMTP fails.
  • Withdrawal is policy-permitted only before approved review, including submitted, queued, grading and review_pending; cancel jobs and preserve audit.
