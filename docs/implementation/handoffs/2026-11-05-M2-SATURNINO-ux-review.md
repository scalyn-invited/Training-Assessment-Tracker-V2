## Findings

| # | Area | Finding | Type | Suggested direction (proposal only) |
|---|---|---|---|---|
| 1 | Sign-in | Password mode shows email and password fields with correct `autocomplete` (`username`, `current-password`) and two plain-language lines for first-time access/forgotten password and for invitations. Banner reads "Synthetic people · Local password sign-in · No email delivery". Clear. | O, C | None. |
| 2 | Sign-in | Submitting sign-in shows a two-stage loading popup. First "Logging in... Please wait." with a spinner (Saturnino's screenshot, `ss signin.png`). If the request is slow it changes to "This is taking longer than usual ... The request may still be processing. Hiding this popup does not cancel it. Please do not submit it again." with a "Hide progress" button (seen in the Claude session), then sign-in completes. Sensible feedback for a slow request. | O | None. |
| 3 | Platform overview | In "System overview" the labels (Identity connection, External email delivery, Live AI) sit on the left and the values ("Password sign-in", "Email is not configured", "AI generation is not configured") sit right-aligned but vertically offset below each label, so a value appears between two labels and the pairing is ambiguous. | O | Align each value on its label's row or stack label over value. |
| 4 | Create account | Form is clear: required markers, "Account operation" (New account / Existing account invitation), Name, Email, "Test account" checkbox ticked by default, "Email is not configured. A private link will be shown for manual sharing.", current password, Reason with helper "Required: explain the change in at least 8 characters." | O | The "Test account" help text mixes audiences ("Local development only"); consider hiding it outside developer environments. Name remains required for "Existing account invitation" in the markup (C); confirm whether it should be. |
| 5 | Create account | "Review and continue" opens a confirmation dialog restating the operation (account, client, "Initial access is Member only and starts after acceptance"), an "I understand the impact of this change" checkbox and Confirm/Cancel, then a "Creating account... Please wait." state. Good pattern for an irreversible action (seen in the Claude session and confirmed in Saturnino's screenshot `Screenshot_21.png`). Two small points: (1) "Confirm change" is a thin red outline while "Cancel" is a filled grey button, so Cancel looks like the stronger choice, and red usually signals a destructive action; (2) the text says "Review the delivery option before confirming", but the delivery note is in the form behind the dialog, not in the dialog. | O | Style Confirm as the primary action and Cancel as secondary; state the delivery outcome in the dialog ("No email will be sent; a private link will be shown"). Check Confirm is announced as disabled until the box is ticked (not checked here). |
| 6 | Private link page | Page states the link is shown once, who to share it with, expiry (one hour; seven days for invitations) and that reissuing cancels the previous link. The link sits in a read-only text box with **no Copy button**. | O | Add a Copy button (must not log or store the value) so the admin does not select by hand. |
| 7 | Setup page | "Set your password: Use at least 15 characters. Saving ends all sessions. You will sign in again." Two fields with `autocomplete="new-password"` and `minlength="15"`. It does **not** say which account the password is for. | O, C | Show the account name/email (not the token) at the top so a person can confirm they are setting the right account. |
| 8 | Setup page, expired-link page | When someone is signed in (tested as the Global Admin), the setup page and the "Link unavailable" page are wrapped in that user's full navigation, client switcher and "Alex · Administrator" header. When nobody is signed in (Saturnino's own screenshot) the setup page shows only the Scalyn header and Theme toggle, so this affects only the signed-in case, for example a shared computer, where it reads as if the signed-in user were changing their own password. | O | Use a minimal layout (no navigation, no signed-in identity) for `/password/setup/*`, `/password/reset/*` and the link-unavailable page, and say clearly if another user is signed in. |
| 9 | Setup page errors | Mismatched confirmation gave a red banner "Please check your input." with "The password field confirmation does not match." Visible and clearly placed, both fields cleared, link stayed valid. The same sentence also appears under the first field, so it is shown twice; the banner text is underlined and appears to link to the field, which is a good accessibility pattern. Wording is framework-default; "The two passwords do not match" would be clearer. Shorter-than-15 input is blocked by the browser's native `minlength` before reaching the server, so the server's own length message was not observed. | O, C | Custom messages for match and length. Check the native validation message is announced. |
| 10 | Invitation | Page text: "Join {client}", "You are signed in as {email}", "Accepting gives you Member access ... Your other clients and training history are unchanged. Sign in again after accepting.", an explicit consent checkbox and a "Leave without accepting" link. Clear. Seen live in Saturnino's screenshot `Screenshot_25.png` (signed in as the invited synthetic account, private window); the text, checkbox, "Accept invitation" button and link all match. The button sits directly above the "Leave without accepting" link with almost no spacing. The page was **not** accepted, so acceptance and the sign-in afterwards were not tested. | O (page), C (accept action) | Add a little space between the button and the link. Not tested: wrong-recipient denial and acceptance. |
| 11 | Link/denial errors | Error copy covers 410 (expired, cancelled or used: "Ask your administrator for a new private link"), 403 (wrong recipient or changed authority) and a general "account or its access has changed" fallback, each with a way back to sign in or account management. **Observed live for 410 only** (Saturnino's screenshot of an expired setup link): title "Link unavailable", the message above and a "Return to sign in" link; it does not say which of the three reasons applies (possibly deliberate), and "Return to sign in" is odd when a user is already signed in. The 403 and fallback cases were not exercised. | O (410), C (403, fallback) | The 403 text is long and mixes two situations (wrong recipient and changed authority); consider splitting. Confirm with Bernie whether the single combined 410 message is intended. |
| 12 | Create account | In Saturnino's browser the New account **Email** box was pre-filled with `admin@example.invalid`, the admin's own login email, and "Your current password" was also filled (Chrome autofill; `option 2.1.png`). The Name and Email inputs carry no `autocomplete` attribute (`local-accounts/admin-panel.blade.php`), so the browser treats the Email box as the login field. An admin could create or invite their own address by mistake. | O (Saturnino's browser), C | Mark the new-account Name and Email inputs so browsers do not fill them (e.g. `autocomplete="off"`); keep `current-password` on the password box. Verify in more than one browser. |
| 13 | Sign-in redirect | After being sent to the login page from `/platform` while not signed in, the page showed "Your sign-in or access has changed. Sign in again with an active account." (`option 2.3.png`). "Changed" is misleading when the person had not signed in. Possible cause not ruled out: the app on port 8000 and the app on port 8157 share the cookie name on `127.0.0.1`, so one may invalidate the other's session. | O (Saturnino's browser) | Say "Please sign in to continue" for a plain unauthenticated redirect; keep the "access has changed" message for a real change. Re-check in a clean browser profile before treating it as a defect. |
| 14 | Client chooser | After sign-in, an account with a single client (seen for two accounts, `Screenshot_23.png` and `Screenshot_24.png`) still lands on "Choose your client / Select the organisation you want to work in" with one button, and the header also shows a "Choose client" dropdown and "Switch client" button, so there are two ways to choose on one screen. The heading, sentence and sidebar are otherwise clear. | O | For a single-client account, go straight to that client; or keep the screen and drop the redundant header chooser. Not tested: accounts with two or more clients (after accepting the invitation). |
